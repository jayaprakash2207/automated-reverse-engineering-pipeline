# Stack Mapping Contract

**Forward Engineering — Document 12 Successor**
**Status:** Binding. Every Backend, Security, and Frontend agent on this project MUST follow the conventions below without deviation. Any departure requires updating this document first, not ad hoc improvisation in a feature branch.

**Confirmed target stack:** Java 17 / Spring Boot 3.x (backend) · React + TypeScript (frontend) · PostgreSQL (database, migrated off Oracle)

**Source of authority:** The original Technology Blueprint (Doc 12) was deliberately technology-neutral — no target stack was named, only capability requirements. This document is the first artifact that resolves those capability requirements into concrete, specific conventions now that the target stack is confirmed. Where Doc 12 stated a hard capability requirement (encryption key management, migration ownership, audit-write guarantees), that requirement is carried forward verbatim into the target convention below. Where Doc 12 was silent on implementation shape (it only ever discussed the legacy/Oracle side, never a target pattern), the target convention is based on common Spring Boot / React best practice, and is marked **[Best practice — blueprint silent]**.

## 1. Core Convention Mapping

| # | Category | Original (Legacy) Pattern | Target Convention (binding) | Basis |
|---|---|---|---|---|
| 1 | **Persistence / ORM** | PL/SQL packages (`PKG-EMPLOYEE`, etc.) and triggers (`TRG_EMP_BEFORE_UPDATE`, `TRG_EMP_INSTEAD_OF_DELETE`) performing data access and side effects directly against `SCHEMA-001`. No app-tier ORM; logic lives in the database. | Spring Data JPA + Hibernate. One `@Entity` per table in `domain/`, one `XxxRepository extends JpaRepository<Xxx, Long>` per aggregate root in `repository/`. **No triggers of any kind are permitted in the target schema.** Row history (e.g. `EMPLOYEE_HISTORY`) is written explicitly by the service layer inside the same `@Transactional` boundary as the mutating operation — never by a DB-side trigger. Entities are never returned from controllers; always map to DTOs. | Doc 12 §3.1: "application-tier-owned migrations... must replace database-trigger side effects." Directly binding. |
| 2 | **Schema migrations** | None — schema evolved via ad hoc DDL/PL/SQL deploys, unversioned. | Flyway. One migration file per change, `V{major}.{minor}__{snake_case_description}.sql` under `src/main/resources/db/migration`. Migrations are the **only** way schema changes reach any environment; no manual DDL against shared databases. | Doc 12 §3.1, reviewable/versioned migrations requirement. |
| 3 | **API routing / controllers** | N/A — legacy exposed no API; access was via Oracle Forms screens directly against the schema. | Spring `@RestController`, one controller per resource/aggregate, class-level `@RequestMapping("/api/v1/{plural-kebab-resource}")`. Method-level mappings use `@GetMapping`, `@PostMapping`, etc. with no verbs in the path (`GET /api/v1/employees/{id}`, not `/getEmployee`). Controllers contain no business logic — they delegate to a `XxxService` and return `ResponseEntity<XxxDto>`. | **[Best practice — blueprint silent]**, but satisfies Doc 12 §3.2's requirement to expose `11_API_CONTRACT_SPECIFICATION.md` contracts over REST. |
| 4 | **Dependency injection** | N/A — PL/SQL has no DI concept. | Constructor injection only. Every `@Service`, `@Repository`, `@Component` uses `final` fields populated via a Lombok `@RequiredArgsConstructor` constructor. **Field-level `@Autowired` is prohibited** — it hides required dependencies and breaks unit-test construction. | **[Best practice — blueprint silent]** |
| 5 | **Input validation** | Implicit / inconsistent, enforced (unreliably) via trigger-based constraints (`TD-11`, `TD-12` — silent/loud failures). | Two-tier validation: (a) structural — Jakarta Bean Validation annotations (`@NotNull`, `@Size`, `@Email`, etc.) on request DTOs, enforced via `@Valid` on controller parameters; (b) business-rule — one dedicated `XxxRuleValidator` class per `BR-*` rule once rule content lands (per Doc 12 §3.2, rules must be "named, independently testable, versioned modules," not scattered annotations or trigger logic). Validation failures never fail silently — they raise a typed exception (see row 9). | Doc 12 §3.1 (`TD-11`/`TD-12` — implicit enforcement is the defect being fixed) and §3.2 (rule externalization). |
| 6 | **Authentication / access control** | None — `PKG-SECURITY.authenticate` is a confirmed bypass. No real auth exists today. | Spring Security 6, stateless JWT bearer tokens (no server-side session state). Passwords hashed with BCrypt (strength 12), never stored or logged in plaintext. Method-level authorization via `@PreAuthorize("hasRole('...')")` on service methods — not just at the controller edge. `USER_CREDENTIALS` is a net-new table/entity designed fresh, per Doc 12's explicit instruction not to assume it exists. SSN and other sensitive columns are encrypted at the application/entity-converter layer (`AttributeConverter`) using a key resolved at runtime from an externalized secrets manager (e.g. AWS/Azure KMS or Vault) — **the encryption key must never appear in source, config files, or the JAR**, replacing the hard-coded AES-256 key defect in `PKG-SECURITY`. | Doc 12 §3.2 ("real authentication/authorization service" as highest-priority gap) and §3.1 (externalized key management, non-negotiable). |
| 7 | **Testing framework / naming** | None confirmed (0/14 CI/CD capabilities present — no evidence of a test suite). | Backend: JUnit 5 + Mockito for unit tests (`XxxServiceTest`), Spring Boot Test + Testcontainers(PostgreSQL) for integration tests (`XxxIntegrationTest`), test methods named `should_<expectedBehavior>_when_<condition>()`. Frontend: Jest + React Testing Library, files co-located as `Xxx.test.tsx`, describe blocks per component/hook, `it("does X when Y")` phrasing. All new code ships with tests in the same PR — there is no legacy suite to extend, so 100% of the target suite is new. | Doc 12 §2 (0/14 CI/CD capabilities, "greenfield CI/CD, not a migration of existing pipelines") + **[Best practice for framework/naming specifics — blueprint silent on shape]** |
| 8 | **Naming convention (casing, files)** | Oracle conventions: `UPPER_SNAKE_CASE` table/package/trigger names (`PKG-EMPLOYEE`, `TRG_EMP_BEFORE_UPDATE`). | Java: packages `lowercase.dotted`, classes `PascalCase`, methods/fields `camelCase`, constants `UPPER_SNAKE_CASE`. Postgres: tables and columns `snake_case` (Hibernate `PhysicalNamingStrategy` set to `CamelCaseToUnderscoresNamingStrategy`), table names plural (`employees`, `employee_history`). REST paths: plural, kebab-case nouns. React/TS: components `PascalCase.tsx`, hooks `camelCase` prefixed `use`, types/interfaces `PascalCase` (no `I` prefix), non-component files `camelCase.ts`. | **[Best practice — blueprint silent]** |
| 9 | **Project / folder structure** | 13 application modules, 6 with zero component-registry entries — legacy module boundaries are largely undocumented and must not be assumed to carry forward. | Package-by-feature, not package-by-layer, at the top level: `com.{org}.{app}.{module}` (one package per confirmed business module, aligned to the eventual `BR-*` rule module boundaries), with layer sub-packages inside each (`controller/`, `service/`, `repository/`, `domain/`, `dto/`, `validator/`). Shared/cross-cutting code lives in `com.{org}.{app}.common`. Frontend mirrors this: `src/features/{module}/{components,hooks,api,types}`, with `src/shared/` for cross-feature code. New modules are added only as their `BR-*` content is confirmed — do not pre-create empty module scaffolding for the 6 opaque legacy modules. | Doc 12 §2 (13 modules, 6 opaque — do not assume undocumented structure) + **[Best practice — folder shape itself is blueprint-silent]** |
| 10 | **Error handling / exceptions** | Errors handled (or dropped) inside PL/SQL packages/triggers; `PKG-AUDIT` confirmed to swallow errors silently (`DISC-006`). | A single exception hierarchy rooted at `ApplicationException` (checked-free, `RuntimeException`-based), with subtypes per failure class (`ValidationException`, `NotFoundException`, `AccessDeniedException`, `BusinessRuleException`). One global `@RestControllerAdvice` maps each to an HTTP status and a structured JSON error body (`timestamp`, `status`, `errorCode`, `message`, `path`, `traceId`). **No exception is ever caught and discarded** — if a handler cannot recover, it rethrows or lets it propagate to the global handler; there is no `catch (Exception e) {}` anywhere in the codebase. Audit-log writes are part of the same transaction as the action they record; if the audit write fails, the parent transaction fails (fail-closed), per Doc 12's explicit prohibition on "swallow and continue." | Doc 12 §3.4 (`DISC-006`, audit must not silently swallow errors — explicitly binding, not deferred). |

## 2. Non-Negotiable Carryovers from Doc 12 (apply across all categories above)

These are Doc 12 requirements that are **not optional best practice** — they are binding constraints inherited directly from the legacy defect analysis, and every agent must treat them as hard gates in code review:

1. **No trigger-equivalent logic.** Do not use Postgres triggers, rules, or `NOTIFY`/`LISTEN` side-effect chains to replicate what `TRG_EMP_BEFORE_UPDATE`/`TRG_EMP_INSTEAD_OF_DELETE` did. All side effects (history rows, derived-field updates) belong in the service layer, explicitly, testably, in the same transaction.
2. **No hard-coded secrets or encryption keys**, anywhere, for any column-level encryption (SSN or otherwise). Keys are resolved at runtime from an externalized secrets manager.
3. **`USER_CREDENTIALS` and the auth/access-control model are net-new design**, not a port of anything from `PKG-SECURITY` — that package's `authenticate` function is a confirmed bypass and must not be treated as a reference implementation of *anything*, including its bugs.
4. **Audit writes fail closed.** An audit-log write failure must fail the parent transaction (or route through a transactional outbox if async is later chosen for a specific workflow) — never log-and-continue.
5. **CI/CD is greenfield.** Because the source system has 0/14 CI/CD capabilities, no pipeline, gate, or test convention here is "migrated" — it is being established for the first time. Backend/Frontend/Security agents should not search for or assume a legacy CI baseline exists to be compatible with.
6. **Do not assume the 30-table schema or 13-module boundary is complete or correct.** (`ASMP-002`, low confidence; 6/13 modules opaque.) Treat legacy schema/module inventories as a floor, not a ceiling — new tables/modules may be required as real requirements surface, and target-side naming/structure conventions above apply to anything newly discovered exactly as they apply to confirmed legacy items.
